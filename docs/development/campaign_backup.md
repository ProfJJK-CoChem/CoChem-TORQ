# Coordinator SQLite backup, recovery and schema adoption

The trusted local service in [campaign_backup.py](../../cochem/orchestration/campaign_backup.py)
creates consistent snapshots of the existing `CampaignCoordinator`, verifies their
bytes and logical inventories, and restores them into a **new, offline, fenced
database**. It does not reconnect workers, reactivate approvals, invent resource
usage, or manufacture scientific evidence.

This implements the local coordinator operational milestone. It does not qualify
remote authentication, scheduler recovery, deployed Codespaces/Actions operation,
unknown historical schemas, or general future schema migrations.

## Online backup and evidence

`create_campaign_backup` uses SQLite's online backup API against the actual source
connection. Committed transactions in an active WAL are included; copying only the
main `.sqlite` file is not used. Concurrent writers remain on the source. The
snapshot is an internally consistent committed database state, not a promise that
it contains every source commit made after the backup completed.

Before publication, verification requires:

- SQLite `integrity_check` returning exactly `ok` and zero `foreign_key_check`
  violations;
- the exact tables, columns, indexes and append-only/terminal triggers generated by
  the installed coordinator implementation;
- supported `user_version` 0 or 1 and, for version 1, the exact adoption metadata
  keys;
- canonical inventories of every table, row count, column identity, ordered row
  content and the AUTOINCREMENT event sequence;
- immutable campaign-plan and task digests, valid finite budgets and allocations,
  dependency and attempt-parent lineage, reservation accounting and event lineage;
- a byte digest of the complete snapshot and a canonical manifest.

The private manifest binds the snapshot to the supplied trusted source-session
identity, source location/inode identity, coordinator implementation hash, actor,
reason and independent recovery-capability hash. Session/location/actor/reason
values are hashed; they are provenance supplied by the trusted caller. They do
not authenticate a remote user or establish molecular-method accuracy.

Files are created exclusively with mode `0600` inside a `0700` bundle. The service
rejects symlinks, extra bundle files, unknown versions, malformed manifests and
unsafe destination directories. Atomic Linux `renameat2(RENAME_NOREPLACE)`
publication prevents overwriting another backup. Files remain mutable by their
owner at the operating-system level; subsequent verification detects mutation.
A trusted manifest hash stored separately is mandatory, so changing the database
and rewriting its manifest cannot silently replace the reviewed backup.

```python
import json
import os
from pathlib import Path

from cochem.orchestration.campaign_backup import create_campaign_backup

created = create_campaign_backup(
    Path("private/live.sqlite"),
    Path("private/backups/backup-2026-10-08"),
    source_session="deployment-session-identity-retained-by-operator",
    actor=f"local-os-user:{os.getuid()}",
    reason="Verified operational snapshot before the reviewed maintenance action.",
)

# Retain this opaque capability privately, outside Git and public artifacts.
capability_path = Path("private/operator-recovery-capability.txt")
fd = os.open(capability_path, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
with os.fdopen(fd, "w") as stream:
    stream.write(created.recovery_authority)
    stream.flush()
    os.fsync(stream.fileno())

# Only the bounded receipt is suitable for sharing. It contains hashes/counts,
# not plans, actor text, process records, worker tokens or operator capabilities.
receipt_path = Path("private/reviewed-backup-receipt.json")
fd = os.open(receipt_path, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
with os.fdopen(fd, "w") as stream:
    json.dump(created.receipt, stream, indent=2)
    stream.flush()
    os.fsync(stream.fileno())
```

The source coordinator's approval, lease, scientific results and accounting are
unchanged by backup. Store the recovery capability and trusted manifest pin
separately; the returned object's representation excludes the capability. Do not
print its fields indiscriminately or upload private database/manifest contents as
public test artifacts.

The deployment-wide [host allocation ledger](host_allocation.md) is a separate
private authority outside the campaign checkout. A campaign snapshot does not
copy, restore or release host reservations. Old host allocations still require
actual PID/create-time termination evidence, including the supported constrained
adapter's independently sessioned native children. Missing launch/death inventory
keeps resources and physical costs unknown; cancelling a restored attempt does
not establish that any original worker stopped.

## Restore policy and worker fencing

`restore_campaign_backup` requires the pinned manifest, the separate recovery
capability, the exact trusted session identity, an explicit recovery actor/reason,
and a new destination with no main file or SQLite sidecars. An optional expected
logical source digest rejects a snapshot that is stale for the required revision.
It never overwrites a live database.

The service copies and reverifies the private snapshot before opening it. A single
transaction then:

1. Revokes every campaign approval and appends a recovery-revocation event.
2. Cancels every unfinished attempt using the coordinator's existing lifecycle
   transition implementation. Each cancellation increments the attempt revision,
   clears the worker lease hash and appends a transition event.
3. Increments every task's next worker-generation fence.
4. Preserves historical terminal attempts, result records, prior events and
   reservation accounting.
5. Checks that no approval, unfinished attempt or worker capability remains active.

The recovered database is checkpointed, moved out of WAL mode, verified again,
fsynced and published atomically only after that transaction has committed. A
failed verification does not publish a destination. Exceptions before commit
roll back the transaction; a process crash before publication may leave a private
staging directory, which is never authoritative or automatically resumed.

```python
from cochem.orchestration.campaign_backup import restore_campaign_backup

receipt = restore_campaign_backup(
    Path("private/backups/backup-2026-10-08"),
    Path("private/recovered-offline.sqlite"),
    expected_manifest_sha256=created.receipt["manifest_sha256"],
    recovery_authority=capability_path.read_text(),
    source_session="deployment-session-identity-retained-by-operator",
    actor=f"local-os-user:{os.getuid()}",
    reason="Offline recovery; original worker liveness and usage are unobserved.",
    expected_source_logical_sha256=created.receipt["inventory"]["logical_sha256"],
)
assert receipt["fresh_campaign_approval_required"] is True
assert receipt["accounting_released"] is False
```

Cancellation in the recovered database does **not** mean an original process
stopped. Backup and recovery leave the source and its running workers untouched.
A source worker with its original legitimate lease may continue against the
source; the recovered database rejects its lease and revoked approval. Switching
a deployed coordinator is a separate operator action that must establish process
ownership, stop/reconcile original work, and prevent competing service instances.

Reservations remain reserved when usage is unknown. The original privately held
operator capability can authenticate the existing `reconcile` operation, which
still rejects an original owned process that is alive. After actual observed
termination, supply `MeasuredUsage` derived from real measurements, with missing
CPU/GPU fields remaining unavailable. The recovery capability does not replace
that operator capability or authorize settlement. Do not enter zero usage merely
to release capacity. Remote ownership still requires its qualified scheduler
adapter; this local milestone does not infer remote-worker death.

Any subsequent calculation requires a fresh `create_campaign` approval, a finite
budget and new task/attempt lineage. There is no operation that silently revives a
recovered cancelled attempt or reapproves a revoked campaign. Old successful
records remain historical evidence and do not become newly executed successes.
Native result files are not contained in the database backup: back them up through
the separately verified immutable artifact-storage service and reconcile their
identities explicitly. No missing native artifact is synthesized.

## One supported migration and rollback

`adopt_campaign_schema_version` implements exactly one migration: introduction of
version-1 metadata to the current, exact known unversioned coordinator schema.
It adds `campaign_recovery_metadata` and sets `PRAGMA user_version=1` in the same
SQLite transaction. The migration records the reviewed pre-migration manifest and
logical data digest, timestamp and actor/reason hashes. Existing campaign,
attempt, approval, result and accounting records remain unchanged.

A genuine verified pre-migration snapshot and its recovery capability are
mandatory. The source path/inode must match, and a `BEGIN IMMEDIATE` transaction
rechecks the entire logical inventory against the backup before any schema change.
A concurrent change after the backup causes rejection. Use a reviewed maintenance
window to prevent such changes rather than silently adopting a newer state.

```python
from cochem.orchestration.campaign_backup import adopt_campaign_schema_version

migration = adopt_campaign_schema_version(
    Path("private/live.sqlite"),
    Path("private/backups/backup-2026-10-08"),
    expected_manifest_sha256=created.receipt["manifest_sha256"],
    recovery_authority=capability_path.read_text(),
    source_session="deployment-session-identity-retained-by-operator",
    actor=f"local-os-user:{os.getuid()}",
    reason="Reviewed introduction of known coordinator schema-version metadata.",
)
assert migration["from_user_version"] == 0
assert migration["to_user_version"] == 1
```

Rollback restores the verified pre-migration backup **into a new, fenced offline
destination** using the restore policy above. It never downgrades or replaces a
live database in place. Rollback intentionally revokes approvals and cancels
unfinished attempts, so it is not a byte-identical live-service resurrection.
Unknown versions or schema shapes are rejected; dedicated reviewed migration
implementations and round-trip evidence are required before supporting them.

## Tests and limits

[The genuine recovery tests](../../tests/test_campaign_backup.py) cover committed
active-WAL snapshots; a concurrent real writer; simultaneous immutable
publication; snapshot/manifest tampering; malformed plans/tasks, accounting and
event lineage; private permissions and symlink rejection; source revision/inode
conflicts; actual running-worker rejection and measured stopped-worker
reconciliation; historical result preservation; both supported versions; and
actual child-process `SIGKILL` before backup publication, restore publication and
schema-migration commit.

The tests use real SQLite files, operating-system processes and mathematical
results. They contain no physical-method substitutes and do not establish
spectroscopic accuracy or deployed recovery readiness. Run them with:

```bash
PYTHONPATH=src:. COCHEM_DISABLE_SANDBOX_CHECK=1 python -m pytest -q \
  tests/test_campaign_backup.py tests/test_campaign_coordinator.py
```

A source-bound deployment release still requires execution in the actual canonical
environments, validated service ownership, native-artifact backup/restore round
trips, resource/quota exhaustion and remote authentication/scheduler evidence.
