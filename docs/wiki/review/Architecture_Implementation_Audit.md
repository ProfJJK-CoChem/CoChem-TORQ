# CoChem-TORQ architecture and implementation evidence review

Review baseline: repository commit `d7a4739a5f7d6f22ed659b32eeb4706bef16225e`. Scope: Comprehensive SRS, Integration Architecture, BASE Draco Blueprint, User Manual, README, packaging, selected execution/storage/UI/provenance modules and tests. References below are repository-relative paths with line numbers at this commit. This is a specification and implementation-gap review, not a certification that the program runs or produces validated chemistry.

## Executive assessment

The available source represents a substantial prototype collection, but it is not evidence of a deployable implementation of the Comprehensive SRS. The main pipeline does not implement the documented cascading refinement contract, engine selection is incomplete, final observables can be synthesized from missing or unoptimized results, distributed completion lacks ownership fencing, and clean installation is underspecified. These are release blockers, not reasons to discard the project. A bounded vertical slice with explicit capability declarations and scientific validity gates is the practical foundation for completing it.

The architecture should retain TOPOS ensemble ownership, TORQ scientific refinement, BASE resource/service ownership, and SpycFit downstream consumption. It should express their boundaries as versioned contracts rather than require all repositories to share Python objects or informal JSON dictionaries. Existing helper modules are candidate implementations to be validated, not completed requirements.

## Evidence levels and performed checks

- **Inspected:** source statements and reachable control flow support the finding; no claim of engine execution.
- **Focused verified:** a small isolated behavior was executed in the current interpreter.
- **Unverified:** files or algorithms exist, but their correctness or integration has not been demonstrated.
- **Missing from reviewed path:** the reviewed entry point does not implement the contract; this is not an assertion that no experimental code exists anywhere.

Two focused checks were run without dependency installation or executing quantum engines. The original `_parse_orca_engrad_or_output` function was extracted unchanged through Python AST and executed with NumPy, synthetic parser input and a temporary directory. This tests parsing logic, not physical validity. The actual `SQLiteTaskQueue` module was imported and exercised against a real temporary SQLite database. Results are in `architecture-focused-checks.json` alongside this review.

The current default interpreter reports NumPy/Pydantic/cryptography available and h5py/filelock/mendeleev/cochem_base/ASE/RDKit/Torch/JAX/qcelemental/qcio/ipywidgets unavailable. This says nothing about a separately prepared environment. No full test suite or live ORCA/CFOUR/PySCF/SLURM/SpycFit run was attempted. Forty-five top-level `tests/test_*.py` files exist; their presence is not proof of behavior. No tracked `.github/workflows` files were found.

## Minimal formal interface contracts to put in the revised SRS

Every envelope needs `schema_name`, `schema_version`, producer version, creation time, immutable ID and content digest. Unknown fields are rejected unless inside an extension namespace. Units are mandatory and normalized at adapter boundaries. Unknown numeric values are absent with an explicit reason; JSON NaN/Infinity and silent coercions are rejected.

| Contract | Required content and invariants |
|---|---|
| `MoleculeRecord` | Stable per-atom IDs; ordered atomic numbers and isotope mass numbers/masses with cited database release; coordinates and units; charge; multiplicity; electronic-state identity; optional connectivity with source and confidence; fragment membership/charge/multiplicity; symmetry constraints. N atoms matches every indexed array. Validate finite values, electron parity and atom mapping. |
| `ConformerEnsemble` | Molecule/state ID; ordered candidates; source run IDs and TOPOS parameters; one energy reference and method per comparison group; degeneracy and provenance; optional probability with thermodynamic/model assumptions. Never rank raw absolute energies from heterogeneous MLFF/GOAT/CREST methods as one ensemble. |
| `MethodSpec` | Stable ID/version; method family and exact functional parameters; orbital and auxiliary bases/ECP; correlation space; relativistic/dispersion/reference settings; engine/version range; supported charge/spin/elements/properties; required tests; approximations and citations. Tier labels are presentation metadata. |
| `WorkflowPlan` | Immutable DAG nodes/dependencies; desired properties; geometry/state/method references; input/output schemas; constrained/unconstrained coordinate definitions; capability report; estimated costs with bounds; stop conditions and finite retry/escalation policy. Planning is side-effect free. |
| `CalculationBudgetContract` | Plan digest; authenticated operator/service identity; allowed engines and resources; max jobs/core-hours/GPU-hours/storage/walltime; validity period; allowed recovery actions; approval event ID. Enforce budget atomically across workers, including retries and child jobs. Hashes prove content integrity; authority derives from authenticated approval and optionally deployment-specific signature. |
| `EngineCapability` | Detected binary path and cryptographic digest/version; supported property/method combinations verified against an adapter test profile; license availability as configured by owner/site; concurrency/precision/device modes; last verification evidence. Unsupported means blocked, not automatic change of physics. |
| `TaskAttempt` | Task/attempt UUID, parent job ID, input/plan digest, lease token/generation, state, resources, engine invocation, start/heartbeat/deadline, stdout/stderr/artifact references, bounded retry reason, timestamps. Use scheduler IDs separately from OS PIDs. |
| `ElectronicResult` | Requested and effective method/state; input/final geometries; success and explicit convergence criteria; optional finite energy, gradients, Hessian, frequency/dipole tensors with units and coordinate frame; parser/version; artifact digests; warnings and diagnostic availability. Gradients identify sign convention; force = negative energy gradient. No default physical values. |
| `ScientificValidation` | Product profile, applicability domain, independent checks passed/failed/not-applicable/unavailable; thresholds with source and units; numerical convergence evidence; uncertainty model/calibration scope; human decisions. Process success and scientific acceptance remain distinct. |
| `SpectroscopicResult` | Isotopologue/state/conformer IDs; Ae vs A0/effective-constant label; mass/axis convention; rotational constants; dipole vector; optional hyperfine tensors for relevant isotopes; centrifugal constants with reduction/representation/convention; covariance/uncertainty and provenance per property; temperature/partition assumptions. SpycFit schema independently validated. |
| `ArtifactManifest` | File/dataset URI, media type, schema version, digest, units, shape/dtype, scientific quantity, parser/engine source, coordinate frame, mapping and lifecycle. Atomic publish of complete result bundle; never point publication manifests at mutable scratch. |

The state machine should minimally distinguish `PLANNED`, `READY`, `BLOCKED`, `QUEUED`, `RUNNING`, `VALIDATING`, `SUCCEEDED`, `PARTIAL`, `FAILED`, `CANCELLED`, `BUDGET_EXHAUSTED`, and `NEEDS_REVIEW`. A separate attempt state machine can map to scheduler states. `SUCCEEDED` is permitted only when all required products pass validation. Completion is idempotent and fenced. Cancel requests propagate to scheduler/process group and preserve useful artifacts. “Exactly once” execution cannot be promised across arbitrary process/network failures; use at-least-once attempts plus deduplicated, idempotent committed results.

## Persistence, provenance and deployment detail

1. **Storage topology:** read-only application installation, task-scoped local scratch, persistent artifact root. Use one documented configuration precedence and canonical variable names; legacy aliases require diagnostics. Existing defaults contradict the README: `cochem/core/config.py:54,74` use relative `./scratch` and `./cochem_tasks.db`; `UI/torq_controller.py:58-59` defaults to checkout-relative scratch. Storage separation improves hygiene but is not confidentiality enforcement.
2. **Atomic publication:** write immutable task bundle to a temporary sibling path, fsync as appropriate, verify hashes/schema, then atomic rename and a transaction that records a committed manifest. Crash recovery discovers uncommitted bundles without fabricating completion. Retain engine inputs, stdout/stderr and parser versions; license-restricted files can be excluded from public bundles with transparent manifest status.
3. **HDF5:** maintain one writer per file. Use predefined schemas and appendable arrays with a commit index; no partial frame becomes visible. Store atom identity, unit attributes, validity masks, method/state references, and precise meanings of uncertainty. Separate immutable publication archives from appendable working stores. Define gzip baseline and optional compression plugins with portable reader support.
4. **Provenance:** SHA-256 is a digest, not a digital signature or proof of scientific correctness. Existing `ProvenanceStamper` supports Ed25519 (`cochem/provenance/provenance_stamper.py:103-151`), but `compute_chunks_sha256:71-98` hashes dataset bytes/path/dtype/shape without dataset attributes such as units; its algorithm is sequential hashing, not an actual Merkle tree. The revised format must cover scientifically meaningful metadata and define canonicalization, verification scope and trusted keys. W3C PROV-O describes relationships; adoption does not itself enforce budget or validate chemistry.
5. **Configuration and resources:** reserve resources from scheduler/cgroup limits; validate aggregate rank × per-rank memory plus runtime overhead. No universal O(Nbas^4) memory model: engines use density fitting/direct algorithms and different tensors. Empirical runtime estimation should expose calibration dataset and prediction intervals. `HPC_Launchers/cochem_submit.slurm:14-15` writes scheduler logs relative to submission directory; its persistent artifacts default to scratch/tmp (`24-30`), requiring explicit retention handling.
6. **Supply chain:** pin supported environments and test wheels outside the checkout. Record dependency lock digest, native library/BLAS/CUDA versions, CPU/GPU, driver, precision and seeds where applicable. Reproducibility means measured tolerances across declared platforms, not universal bitwise identity. Build signatures are useful only with trusted-key and revocation procedures.
7. **Engine licensing:** discover authorized locally provisioned binaries and follow actual vendor/site distribution terms. Do not invent `ORCA_LICENSE_HASH`/`CFOUR_AUTH_TOKEN` authentication protocols. A missing licensed engine is a blocked capability; a different scientific method is a new plan requiring declared user policy. Software licensing is not derived from OSI rules for proprietary tools.
8. **Operations:** structured redacted logs with job/attempt IDs; health/readiness; resource/disk alerts; per-job retention and deletion; backup and restoration of manifests/state; migrations with compatibility tests; cancellation and orphan reconciliation; restart/resume acceptance evidence. Telemetry must not include confidential molecular coordinates or secrets by default.

## Architecture improvements: safe changes versus decisions

Safe specification changes: deduplicate chapters and remove agent-transcript debris; stable requirement IDs; separate normative requirements from commentary; typed versioned contracts; explicit evidence/status labels; distinguish digest/signature; one method registry; schema/unit checks; truthful missing-data handling; finite budgets/retries; capability-driven engine selection; conditionally applicable properties; explicit local/cluster deployment profiles; test evidence and rollback gates. These clarify meaning without committing to a new scientific model or platform.

## Implementable phases with exit criteria

- **P0 — Specification and baseline control.** Resolve precedence among SRS/matrix/manual, assign requirement IDs, publish schemas and method registry, identify required versus optional capabilities, state current implementation gaps. Exit: machine-checkable traceability and no contradictory normative contracts.
- **P1 — Correct local vertical slice.** Install a wheel in a clean environment; `doctor`, validate, plan and one local engine adapter; unoptimized input → real optimized geometry → convergence/Hessian evidence → Ae/dipole → validated export. Handle failures without synthetic values. Exit: successful real small-molecule calculations plus missing/truncated output, wrong units, invalid charge/spin, absent binary, failure, timeout and cancellation tests.
- **P2 — Durable orchestration and storage.** Fenced queue, immutable attempts, atomic artifact publication, budgets, idempotent restart and single-writer store. Exit: kill/restart at each boundary, stale completion rejection, no duplicated committed result, no lost successful artifact, bounded resource use and backup/restore.
- **P3 — Ensemble refinement and PES.** TOPOS contract, approved coordinate domain, consistent energy grouping, grid/adaptive scanning, constraints, symmetry and topology monitoring, TS/IRC where requested. Exit: reference landscapes, permutation/rotation invariance, numerical step/grid convergence and reproducible branch selection.
- **P4 — Spectroscopic corrections and downstream interoperability.** Validated CFOUR/other property adapters, VPT2 where applicable, rotor/DVR profile, isotope transformations, SPCAT/SpycFit contracts. Exit: convention-aware reference comparisons, uncertainty scope, finite-field/finite-difference checks, unsupported-domain rejection and authentic downstream read/render.
- **P5 — Deployment profiles.** BASE UI via same backend API, authorized Slurm cluster, optional container/GPU adapters. Exit: clean provisioned Linux baseline; declared additional platform tests; scheduled cancellation/resume, multi-user isolation if offered, locked environment, operations and rollback runbooks.
- **P6 — Research extensions.** Learned acceleration, multireference automation, advanced real-space analytics, Open OnDemand/RTC and higher-dimensional nonrigid models. Each requires a preregistered acceptance benchmark, licensed/available backend, scientific review and bounded resource policy. These are not blockers for the scoped baseline, but cannot be claimed complete in the full-program release until individually accepted.

No phase is accepted merely because its source file exists or imports. Full program readiness requires all mandatory profile requirements and the applicable scientific benchmark/interop/deployment gates to pass with recorded evidence.
